# Selected release: Next.js and independent analysis workers

This is preparation, not an AWS/Jenkins deployment receipt. The selected release frontend is **Next**, replacing Vite in the new `docker-compose.next.yml`/Jenkins path. Existing Vite source/development Compose and `docker-compose.prod.yml` remain for compatibility and rollback planning; they are no longer the selected new release. Never run both production Compose files as competing control planes on the same database. The API's existing AgentRegistry/effect execution still supports one API process. Six structured analysis roles use a minimal worker image; Support uses the full backend image for retrieval. All seven use the same source and independent role configuration and use durable Mongo messages; containers alone are not proof of distributed execution (see the separate process test).

## Images and build gates

From the repository root:

```bash
docker build -t REGISTRY/startup-simulator-backend:FULL_COMMIT backend
docker build -f backend/Dockerfile.worker -t REGISTRY/startup-simulator-role-worker:FULL_COMMIT backend
docker build -f web/Dockerfile -t REGISTRY/startup-simulator-next:FULL_COMMIT .
docker build --build-arg CADDYFILE=Caddyfile.next -t REGISTRY/startup-simulator-caddy-next:FULL_COMMIT docker/caddy
```

Next's root-context multistage build installs only web dependencies, copies the shared source/test files, executes unit/build/type checks and packages standalone output. Runtime runs as Node's unprivileged user. `.dockerignore` excludes configured env files, local databases/uploads, build output and node_modules. Next serves a per-request nonce CSP, including hydration/chunk scripts, and keeps HTML private/no-store. Static media retains its explicit cache headers. No permissive script unsafe-inline workaround is used. Caddy's Next configuration proxies frontend:3000, /api and authenticated /mcp and leaves the HTML nonce policy to Next. Existing Vite Caddy policy is preserved in its own file.

The minimal worker uses only the existing pinned context/queue dependencies and runs as UID 10001. It contains no Torch/Chroma/models; its six configured structured roles do not need them. Support retains the full model-capable backend image. Backend builds normally preload decision-memory/embedding/reranker models and fail if that acceptance cannot be fulfilled. `--build-arg PRELOAD_MODELS=0` is an explicit **local rule/fallback-only build**, not equivalent ML readiness. Runtime downloads remain disabled; model-backed retrieval must be evaluated before promotion. CPU-only Torch is retained. Corporate proxy builds may pass Docker's predefined proxy build arguments, a host mapping for an otherwise unresolvable proxy, and `--secret id=build_ca,src=/path/to/trusted-ca.pem`; the optional read-only public CA mount retains TLS verification and does not copy proxy credentials or the CA into runtime layers. Do not disable certificate validation. Local network diagnosis, actual results and remaining blocked gates are in the impact/evaluation records.

## Credentials, volumes and existing users

Review `docker/next.env.example` and merge required values into a protected deployment environment file. Do not overwrite existing configured `.env`. API signing/vault keys and existing Mongo root credentials must remain consistent with the data they protect. Worker signing/vault values must differ from API keys; workers receive no provider keys. Worker Mongo uses a separate `analysis_worker` user with read-only context access and job/heartbeat updates, **no financial/task/account/credential writes or credential/user reads**. `docker/mongo/analysis-user.js` initializes a fresh database only. For an existing volume, after backup an authenticated admin must explicitly apply that reviewed script with MONGO_WORKER_PASSWORD available inside Mongo; existing worker passwords are intentionally not silently replaced. Verify grants before starting workers. Least-privilege API database credentials are a further hardening task; this topology retains the pre-existing root API connection.

Set the exact existing Mongo/Chroma/upload Docker volume names explicitly; these are external volumes and Compose refuses missing volumes. For a fresh isolated rehearsal, create distinct new volumes deliberately. Do not reuse a production volume for tests. `check_worker_permissions.py` creates/removes only its own uniquely named disposable Mongo container and anonymous volumes, never the configured database.

Supabase: configure Site URL to the HTTPS origin and allow `/auth/callback` and `/auth/confirm` redirects as required by the project auth flow. Use a publishable/anonymous key, never a service-role key. Verify signup confirmation and existing-account linking with controlled identities. Supabase identity accounts and legacy native passwords are different; follow the existing explicit verified linking flow. Nothing here migrates or relinks accounts automatically.

## Preflight and startup

1. Complete backups and an isolated restore rehearsal. Record exact image digests/full commit tags, volume names and current configuration location securely.
2. Validate environment without printing expanded secrets: `docker compose --env-file /secure/release.env -f docker-compose.next.yml config --quiet`.
3. Check domain DNS, AWS security group 80/443, restricted SSH and outbound provider/model access. No API/database/worker host ports are published. Mongo is authenticated; Redis is optional and unnecessary for role correctness.
4. Start an explicitly authorized staging deployment with the prepared environment. `scripts/deploy.sh` accepts only full 40-character commit tags, pulls, waits for health and retains previous images/volumes. It uses the configured `.env`; if your environment is elsewhere, export it securely or use Docker's COMPOSE_ENV_FILES setting. Do not pass secrets on the command line.
5. Verify HTTPS `/api/health` reports Mongo connected. Check frontend health and individual worker heartbeats; health proves connectivity, not AI quality or correct business decisions. Worker health is per container hostname and becomes stale after 60s.
6. Check logs for safe failures, owner sign-in, cross-tenant denial, 3D/fallback, document citation freshness, seeded seven-role analysis, owner revisions/approval, execution results and JSON/CSV exports. No test email, real publication or payment is authorized by this runbook.

## Backup, restore and rollback

Enter a maintenance window and stop frontend/API/analysis workers so application writes cease. Do not remove Mongo or volumes. With `umask 077`, an authenticated Mongo `mongodump --db startup_simulator --archive --gzip` inside the Mongo service produces a protected archive. Use the container's existing root environment values without echoing them. Back up Chroma and uploads as consistent filesystem archives while the API is stopped; retain vault key material separately in your secret manager, never in logs or the repository. An archive without the original encryption key cannot recover stored provider credentials. Store encrypted copies off-host with retention/access controls.

Restore first into a **new isolated Mongo database/volume**, using `mongorestore` namespace remapping; restore Chroma/uploads into new isolated volumes. Verify counts, representative task/ledger records, identity ownership, citations and files, then test the app against that isolated restore. Never test restore by overwriting production. The disposable Mongo permissions script verifies a real dump/remapped-restore comparison; Chroma/upload volume restoration and real production backups remain operator acceptance gates.

For code rollback, stop writes, select previous known-good full-commit image tags in the protected environment and run the same selected Compose health startup. Never use `latest`, `down -v`, image pruning or destructive database reversal as rollback. New collections are additive; evaluate compatibility before sending newer jobs to an older API. Cancel/settle new analysis runs before rolling back to code without their worker contracts. Restore data only after an explicit recovery decision, using the verified backup and isolated restore plan.

## Jenkins execution path

The existing Jenkinsfile now checks out, derives full commit tags after checkout, builds the normal cached-model backend, builds the minimal role-worker image, launches real isolated Mongo for backend/process tests, evaluates hybrid retrieval, builds/tests Next, validates Next Caddy and runs scripts/smoke_next_release.py against uniquely named isolated volumes with provider keys forced empty. It no longer builds Vite or pushes mutable latest tags. Publishing/deployment default to disabled. Required controller capabilities: Docker/Compose, Python 3 for the stdlib-only isolated topology script, Git, Pipeline, JUnit, Credentials Binding, AWS Credentials, SSH Agent; outbound dependency/model access and sufficient storage/RAM. Required production credentials: `aws-ecr-creds`, `ec2-deploy-key`, and a verified `ec2-known-hosts` secret file. Set AWS_ACCOUNT_ID/AWS_REGION and EC2_HOST/EC2_USER/EC2_DEPLOY_PATH; prepare the exact matching scripts/configuration checkout and protected environment on that host. SSH host checks remain enabled.

Run with DEPLOY_TO_PRODUCTION=false first; retain the Jenkins build URL, commit, test XML, image digests and stage logs. A Groovy file review or GitHub green check is not controller execution. GitHub's production fixture browser gate remains separate. Only an authorized later rollout may enable image publication/deployment. No controller run, ECR push, EC2 resource or live URL is inferred here. AWS instance sizing must follow measured full-stack memory/CPU, including model loading; the rule-only local profile is not a sizing estimate for seven ML-loaded workers.
