# Proposed architecture

## Deployment decision
Start with a modular FastAPI business application plus separately running worker, MCP service and realtime gateway. Five business roles are modules, not five obligatory microservices. Modules: identity/access, work/approvals, departments, integrations, knowledge, notifications and audit. Extract a module only when measured load, isolation or ownership justifies independent deployment.
Next.js TypeScript frontend → FastAPI APIs → authoritative MongoDB data. Approved work → durable outbox → Redis/Celery worker → MCP tools/provider adapters. Provider webhooks → verified inbox → workers → database → realtime notifications → UI/CEO projection.

## Stack decisions
Next.js App Router, TypeScript, Tailwind and shadcn/ui with one primitive family (Radix where selected). TanStack Query for server state, Zustand only for transient UI preferences, React Hook Form/Zod for forms, TanStack Table for work lists, date-fns/date-fns-tz for dates, Recharts for metrics. Keep 3D boardroom optional using existing Three/React Three Fiber capabilities after compatibility review. Avoid mixing Chakra, MUI and shadcn component systems.
FastAPI/Pydantic/LangGraph/Groq remain. Supabase Auth replaces custom login gradually; MongoDB remains the business source of truth initially. Supabase Auth does not add MongoDB row-level security: enforce tenant authorization in backend repositories on every read/write, worker and MCP call. Supabase Postgres consolidation is a later explicit migration decision, not a second source of truth.
Redis for short-lived cache, distributed rate limits and Celery broker. MongoDB outbox/inbox and task records provide recoverable business truth. Configure Redis persistence and broker loss recovery; never treat Pub/Sub as a durable task queue. Separate eviction-friendly cache Redis from broker Redis in production. Celery delivery is at least once: idempotent workers and provider reconciliation remain mandatory.
python-socketio ASGI gateway and socket.io-client for realtime, with compatible Python Redis manager when scaling. Node Redis adapter documentation is not a Python configuration recipe. Authenticate rooms using server-derived tenant membership. Persist event sequence; reconnect fetches missed updates through API. HTTP polling fallback needs session affinity across instances; test chosen transport deployment.
Resend for app mail; Gmail or Microsoft Graph for mailbox access; Google Calendar or Microsoft Graph for calendar. Object storage for attachments with signed access and content scanning. Chroma remains initial vector store; add lexical index and reranker behind retrieval interface.

## MCP contract
Backend is host with MCP client. One authenticated private MCP server initially exposes scoped tools/resources. Split by trust boundary later, not by agent label. Typed tools include get_budget, search_knowledge, propose_task, get_task_status, calendar_freebusy and create_email_draft. Side-effect tools accept approved_task_id and payload version; server independently verifies tenant, actor, approval, expiry and idempotency. Separate approval service credentials from agent credentials; agents cannot forge approvals. External adapters use least-privilege credentials from server vault. Prefer Streamable HTTP for separately deployed server; local stdio is suitable for development. Allowlist endpoints and tools; enforce timeouts, output size and egress restrictions. Log invocation metadata without secrets.

## Data model and indexes
Collections: businesses, memberships, objectives, tasks, task_versions, approvals, policies, budget_accounts, ledger_entries, reservations, integration_accounts, credentials, webhook_inbox, outbox, execution_attempts, artifacts, candidates, meetings, campaigns, notifications, documents, chunks, evaluations, audit_events.
Indexes: unique tenant+task_id; tenant+status+due_at; tenant+objective_id; unique provider+account+webhook_event_id; unique tenant+idempotency_key; tenant+created_at audit; document_id+version+chunk_id; tenant+candidate email under retention policy. TTL only on ephemeral tokens/cache, not audit or business evidence. Enforce unique reservations and atomic budget checks. Use MongoDB transactions on replica-set deployment for task/approval/outbox invariants. Do not rely on process-local locks across workers.

## Reliability and integrations
Verify webhook raw-body signatures and timestamp tolerance, dedupe events, store durable inbox before acknowledging, enqueue and process asynchronously. Tolerate duplicates, reordering, retry and account revocation. Poll provider when webhook evidence is missing. Never trust webhook tenant_id; resolve tenant from registered provider account.
Outbox publisher retries safely; workers claim leases, heartbeat, recover abandoned jobs and use bounded exponential retries with jitter. Terminal failures enter a dead-letter workflow with human replay controls. External success followed by DB failure creates reconciliation-required state, never blind repeat. Every request carries trace_id, task_id, tenant_id and attempt_id.
Cache only authorized scoped keys; invalidate on writes; do not cache credentials or private pages publicly. Use per-user/tenant/provider rate budgets and AI concurrency limits. Cap tokens and tool-loop iterations.

## Security, networking and scaling
Validate Supabase JWT signature/issuer/audience/expiry; map subject to membership; roles owner/admin/member/viewer with action permissions. MFA for high privilege, explicit CSRF/session protection for cookie-authenticated mutations, restricted CORS, no service keys in browser. Protect attachments, candidates and tokens; enforce retention/deletion. WAF/reverse proxy covers ingress; firewall keeps Mongo/Redis/MCP private; egress allowlist controls provider destinations. None replaces authorization.
Initial Docker Compose environment: web, API, worker, scheduler singleton, MCP, Redis and Mongo replica set. TLS reverse proxy handles routing. Scale stateless API independently; workers by queue age; bound DB pools. Kubernetes later: deployments, services, ingress, secrets, network policies, probes, resource requests/limits, HPA, worker autoscaling, persistent services/managed DB, rolling deployment and rollback. Do not claim a need for millions of users or measured capacity without load testing.

## Delivery and monitoring
CI: lint, types, unit tests, backend integration tests, approval/tenant tests, frontend build, contract tests, dependency and secret scans. CD: staging deploy, migrations, smoke tests, controlled production promotion, image rollback and tested backup restore. Use OpenTelemetry traces, structured logs, Prometheus/Grafana metrics and Sentry errors where deployment supports them. Monitor queue age, overdue jobs, webhook lag, duplicate suppression, provider failures, AI cost/latency, retrieval quality and auth failures. Proposed SLOs must be benchmarked before adoption.
